# M03-M09 sequential MVP delivery plan

This plan continues the accepted M0-M2 architecture. It is deliberately
sequential: a module may begin only after the previous module is accepted,
merged to `main`, and tagged.

## Cross-module invariants

Every module must preserve these rules:

- REST APIs remain under `/api/v1`.
- Streaming run events use SSE.
- PostgreSQL remains the business store, transactional Outbox, and MVP queue.
- GitHub, Agent Compose, and Agent providers stay behind adapters.
- Preserved GitLab code remains behind `REPOMENDER_FEATURE_GITLAB=false` and is
  excluded from active M3-M9 real-provider acceptance.
- All state changes enforce authenticated sessions, RBAC, CSRF where
  applicable, input limits, secret redaction, and audit recording.
- Agent output is untrusted input and must be schema-validated.
- Agent execution never merges automatically and never writes to a default or
  protected branch.
- Network access, repair plans, and patch publication use the approval rules
  defined by their module.
- Every new product surface remains behind its module feature flag until the
  acceptance gate passes.
- Real model credentials exist only in Agent Compose.

The shared gate for each module includes:

```text
Frontend: ESLint, typecheck, component/SSR tests, production build
Go: unit tests, race detector, go vet, API integration tests
Database: migrate/rollback, constraints, transactions, concurrency
Contracts: recorded provider fixtures and error-response matrix
E2E: clean Docker Compose environment from an empty database
Real smoke: dedicated provider and AC environments
Security: RBAC denial, signatures, redaction, limits, audit evidence
```

Record commands and evidence in `docs/acceptance/M0X.md`.

## Deferred GitLab policy

GitLab OAuth, synchronization, webhook, schema, and fixture work completed in
M2 must not be deleted or allowed to decay. Contract and clean-stack regression
tests continue to run with the deferred flag explicitly enabled. Product UI,
runtime registration, and real-provider acceptance remain GitHub-only until a
future scoped decision restores GitLab.

## M03 — Agent Compose execution adapter

Branch: `feature/m3-ac-execution-adapter`

Feature flag: `REPOMENDER_FEATURE_M3_AC_EXECUTION`

Tag after merge: `m3-ac-execution-adapter-mvp`

### Minimal MVP

- Define a provider-neutral execution adapter and a concrete Agent Compose
  adapter.
- Discover and document the actual AC API/version contract before committing
  RepoMender interfaces.
- Add AC health and compatibility checks to readiness without making liveness
  depend on AC.
- Start one Codex task with an explicit repository, immutable commit, prompt
  template, time limit, and resource policy.
- Stream normalized status, log, test, and Agent-activity events to RepoMender
  over SSE.
- Support cancellation and deadline expiry.
- Map AC transport, unavailable, incompatible-version, rejected, timeout,
  cancellation, sandbox, Agent, and malformed-result failures into stable
  RepoMender error codes.
- Redact credentials and configured sensitive patterns before persistence or
  streaming.
- Add an internal execution diagnostic page; do not expose M4 task management
  prematurely.

### Data and interfaces

- AC endpoint/version configuration and compatibility policy.
- Execution correlation identifier and normalized event envelope.
- Adapter methods for health, start, event stream, cancel, and final result.
- Structured final-result schema with versioning.

### Acceptance

- Complete one real Codex execution in a real AC daemon.
- SSE receives the ordered terminal event sequence.
- Cancellation stops the AC task and produces one terminal state.
- Offline AC, incompatible version, timeout, malformed event, dropped stream,
  and redaction fixtures pass.
- Service restart/reconnect behavior is documented and tested.

## M04 — Task, run, queue, and audit core

Branch: `feature/m4-task-audit-core`

Feature flag: `REPOMENDER_FEATURE_M4_TASKS`

Tag after merge: `m4-task-audit-core-mvp`

### Minimal MVP

- Add `Task`, `Run`, `RunEvent`, `Finding`, `Evidence`, and `AuditEvent`.
- Implement task kinds `code_review`, `ci_diagnosis`, and `issue_repair`
  without yet enabling their business triggers.
- Implement the canonical task state machine:
  `queued`, `running`, `awaiting_approval`, `succeeded`, `failed`,
  `cancelled`, and `superseded`.
- Use PostgreSQL row locking and lease/heartbeat semantics for the persistent
  worker queue.
- Add bounded retry with retry classification, backoff, and idempotency keys.
- Persist AC event streams and expose task/run list, detail, cancel, retry, and
  SSE APIs.
- Replace task/run UI mock data with real API data.
- Record immutable actor, action, resource, outcome, correlation, and metadata
  fields for audited operations.

### Acceptance

- Restart API and workers mid-task without losing or double-running work.
- Reject every illegal state transition.
- Verify concurrent workers claim a task exactly once.
- Verify retry, cancellation, supersession, and terminal idempotency.
- UI renders real list/detail/SSE state without task mocks.
- Auditor can read audit evidence but cannot mutate tasks.

## M05 — Code review

Branch: `feature/m5-code-review`

Feature flag: `REPOMENDER_FEATURE_M5_CODE_REVIEW`

Tag after merge: `m5-code-review-mvp`

### Minimal MVP

- Normalize GitHub pull request events.
- Create one review task per repository and immutable head commit.
- Deduplicate repeated deliveries and supersede an older non-terminal review
  when a new head commit arrives.
- Fetch repository content through SCM adapters and check out the exact commit
  inside AC.
- Produce schema-validated findings with severity, category, path, line/range,
  explanation, evidence, confidence, and suggested remediation.
- Publish a GitHub Check and pull-request summary through the SCM adapter.
- Show overview, findings, evidence, tests, Agent activity, and publication
  state in the UI.

### Acceptance

- One real GitHub PR completes review.
- Published results point to the exact reviewed commit.
- Duplicate delivery creates no duplicate review/publication.
- New commit supersedes the old result.
- Missing commit, fork permission, deleted branch, malformed finding, rate
  limit, and publication failure have controlled outcomes.

## M06 — CI diagnosis

Branch: `feature/m6-ci-diagnosis`

Feature flag: `REPOMENDER_FEATURE_M6_CI_DIAGNOSIS`

Tag after merge: `m6-ci-diagnosis-mvp`

### Minimal MVP

- Trigger from failed GitHub Actions workflow runs.
- Fetch logs and metadata through SCM adapters with strict size/time limits.
- Redact tokens, secrets, credentials, and configured patterns before
  persistence or AC prompts.
- Chunk oversized logs while preserving stable line/source references.
- Let AC analyze and, where permitted, reproduce the failure at the immutable
  commit.
- Produce root-cause hypotheses with evidence, confidence, affected component,
  reproduction result, and recommended next action.
- Publish a concise provider summary and render full evidence in RepoMender.

### Acceptance

- Real/recorded GitHub Actions failure fixtures identify the intended root
  cause and evidence.
- Large logs, binary output, missing logs, expired logs, permission denial,
  rate limits, cancellation, and non-reproducible failures are controlled.
- Redaction tests prove known secrets never reach stored logs, SSE, prompts, or
  provider comments.

## M07 — Approval and governance

Branch: `feature/m7-approval-governance`

Feature flag: `REPOMENDER_FEATURE_M7_APPROVALS`

Tag after merge: `m7-approval-governance-mvp`

### Minimal MVP

- Add the reusable `ApprovalRequest` state machine for `repair_plan`,
  `publish_patch`, and `sandbox_network`.
- Support pending, approved, rejected, expired, cancelled, and consumed states.
- Add risk levels, expiry, requested action digest, requester, eligible roles,
  decision actor, decision reason, and immutable timestamps.
- Require idempotency keys for approval decisions and action consumption.
- Bind approvals to an exact action digest so changed plans/patches require a
  new approval.
- Enforce Admin/Maintainer approval policy and Developer/Auditor denial.
- Add approval inbox/detail UI and complete immutable audit evidence.

### Acceptance

- No protected action executes before a valid approval is consumed.
- Repeated approval/consumption requests are idempotent.
- Unauthorized roles return 403 and create denial audit evidence.
- Expired, rejected, altered, or already consumed approvals cannot execute.
- Network approval constrains the exact requested destinations/policy.

## M08 — Issue repair

Branch: `feature/m8-issue-repair`

Feature flag: `REPOMENDER_FEATURE_M8_ISSUE_REPAIR`

Tag after merge: `m8-issue-repair-mvp`

### Minimal MVP

- Trigger from an eligible GitHub issue or an M6 diagnosis.
- Generate a structured repair plan at an immutable base commit.
- Pause for the first `repair_plan` approval.
- After approval, execute the repair in AC, generate a patch, run configured
  tests, and collect evidence.
- Validate patch paths, size, binary policy, generated files, protected files,
  and secret scanning results.
- Pause for the second `publish_patch` approval bound to the exact patch digest.
- Publish only to a new non-protected branch and open a draft PR.
- Never merge and never push to the default/protected branch.

### Acceptance

- One GitHub issue completes:
  plan → approval → patch/tests → approval → draft PR.
- Changed base commit, changed patch, failed tests, secret detection, unsafe
  path, oversized patch, publication retry, and provider failure are controlled.
- Draft publication is idempotent and fully audited.

## M09 — Automation and administration

Branch: `feature/m9-automation-management`

Feature flag: `REPOMENDER_FEATURE_M9_AUTOMATIONS`

Tag after merge: `m9-automation-management-mvp`

### Minimal MVP

- Add templates for code review, CI diagnosis, and issue repair.
- Configure enabled state, repository scope, event filters, Agent template,
  execution budget, timeout, concurrency, risk, and approval policy.
- Validate configurations before activation and version every published change.
- Ensure disabled automation never schedules new work.
- Add automation list/editor/detail UI and run history.
- Add administrative views for SCM/AC health, retention settings, Agent
  templates, budget use, and audit lookup.
- Apply changes transactionally and record who changed which version.

### Acceptance

- Each template saves and triggers its real workflow in the scoped repository.
- Disabled automation produces no new task.
- Invalid provider/event/budget/approval combinations cannot be published.
- Concurrent edits do not silently overwrite one another.
- Historical runs retain the exact configuration version used.
- RBAC and audit coverage pass for create, edit, publish, disable, and delete.

## Completion boundary

M9 completion does not authorize starting enterprise hardening implicitly.
M10 requires a separate accepted plan covering installation, upgrades, backup
and restore, metrics, OpenTelemetry, rate limiting, retention enforcement,
security baseline, and load testing.
